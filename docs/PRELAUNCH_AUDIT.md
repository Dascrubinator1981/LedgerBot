# LedgerBot prelaunch re-audit

## Decision

**NO-GO for real financial data, a hosted real-user beta, or public launch.** Local synthetic development/testing may continue. This is an engineering re-audit and regression run, not an independent penetration test, accessibility certification or completed production migration. No app publication, deployment, bank connection, billing activation or real customer-data use occurred.

The next implementation task is specified in [CODEX_PRIVATE_BETA_PROMPT.md](CODEX_PRIVATE_BETA_PROMPT.md). That prompt is a staged work order, **not a statement that the listed work has been performed**. It explicitly requires a report and separate owner approval before any deployment/publication.

## Scope and evidence

Reviewed the existing instruction contract, current service/domain/auth/database/HTTP code, human review UI, route handlers, package/CI configuration, release matrix and tests. Used the installed Next.js route-handler and data-security documentation. Existing build baseline: commit `112e755` on `feat/manual-finance-foundation`; this audit adds a follow-up commit. All fixtures are fabricated. No `.xlsx`, SQLite database or `.env.local` file is tracked.

Eight targeted regression tests were written and run against the earlier implementation: **8 failed**, reproducing budget identity drift, stored-draft digest verification omission, backwards reconciliation, non-atomic discard, negative-zero presentation, cent rounding at the safe-integer boundary, cash-coverage misclassification and unbounded forecast horizon. These failures were fixed rather than skipped. Additional tests cover error sanitization, exact aggregate arithmetic and post-commit refresh failure.

## Efficiency improvements and remaining limits

The forecast now binary-searches to the first relevant future occurrence rather than walking through every historic occurrence from its start. It computes the end date once, groups event amounts by day and accumulates the daily path once. A long-history month-end fixture verifies anchor and clearing-delay behavior. This is an algorithmic improvement; no production latency/load guarantee is claimed.

Proposal validation no longer reloads full proposal history or duplicates its financial-state load during creation. Revision checks use a scalar query; reconciliation avoids loading proposal history. The browser still receives the complete ledger/history state and recalculates views, and SQLite uses synchronous operations. Large-volume pagination, database indexes/aggregates, coherent feature components and tenant-safe caching should follow the Postgres migration, rather than over-investing in the temporary SQLite store. No numerical speedup or capacity claim has been measured.

## Launch blockers in priority order

1. **High — hosted identity and database boundary:** SQLite has no RLS. Managed Postgres/Supabase auth/RLS, verified email/recovery/session lifecycle, proper abuse controls, least privilege, TLS/origin/cookie verification and actual database-role negative tests are not implemented/tested.
2. **High — financial forecast completeness:** no occurrence-to-actual matching, recurring schedule CRUD, explicit unpaid/current-day/overdue obligations or user timezone policy. Future recurrence estimates can overlap pending/recorded activity; calendar dates must never imply actual clearing. The UI now states this limitation directly. Do not use forecasts for real decisions yet.
3. **High — private-data lifecycle:** drafts/before snapshots lack application encryption/key rotation/retention, export/privacy deletion/restore/undo and tested backup/recovery. Real records must not be entered before these policies and controls exist.
4. **High — outcome recovery and production concurrency:** receipt/status lookup with stable retry identity across reload/lost responses, multi-worker race/rollback tests, production SQL constraints and migration upgrades remain outstanding. The new rollback tests use actual SQLite failure injection, not hosted Postgres.
5. **Medium — manual workflow completion:** paired pending-transfer settlement/editing, opening correction/rebase, stable account/category renaming, full intraday running balances and richer reconciliation investigation remain incomplete. The current transfer pair can be deleted/recreated only when unreconciled; this is not a finished settlement flow.
6. **Medium — accessibility/product QA:** dedicated navigation/routes, per-item setup reminders, cross-browser testing, screen-reader/switch/eye-gaze/real touch QA, zoom/contrast checks and an independent WCAG/security/privacy review are open. Passing Chromium keyboard/mouse tests is not conformance certification.
7. **Medium — development dependency advisory:** full `npm audit` exits 1 with **16 moderate findings** propagated from `minimatch <11.0.1` (GHSA-g3hv-75wg-m249), through ESLint and its plugins. Production-only audit reports zero. Installed consumers require minimatch 3.x/10.x; patched upstream is 11.x. Registry metadata reports ESLint 10.14.0, but the latest import/react/accessibility plugins declare ESLint 9-or-earlier compatibility. No compatible repair was established; no forced downgrade, cross-major override, disabled rule or advisory suppression was applied. Update the supported lint/plugin chain and retest, or obtain an explicit reviewed risk decision before release. CI now includes the full audit, so this failure remains visible rather than hidden by production-only coverage.
8. **Release gate — operations and review:** remote CI/PR state unverified while GitHub API access is blocked; no staging deployment, production backup/restore, monitoring/incident drills or owner-approved privacy/terms/release checklist. No deployment should be inferred from a successful build.

AI, voice, OCR, bank sync, subscriptions, payments and MCP remain disabled. They are later scope and are not needed to finish the manual-finance private-beta candidate. No vendor registration/key is needed for current local testing.
