# LedgerBot staged implementation — review candidate

**Not deployed. Fictional data only. NO-GO for a real-user private beta and for public launch.** These are tested implementation checkpoints, not a claim that the complete four-stage contract or master product specification is finished.

## What you would see today

You would register an empty workspace and, in PostgreSQL mode, verify your email first. You could create your own accounts, categories and monthly targets, enter expenses, income or refunds, split them, pay a card through a paired transfer, and review every financial change before it becomes real in the ledger. Unknown balances remain unknown. Pip and external integrations are explicitly disabled.

Entering an approved expense updates your account balance, budget actuals and chart from the same stored ledger. Your monthly target stays a plan; changing it cannot create cash. Spending outside a target or category still counts in the overall comparison. “On plan,” pacing and “Over budget” use exact cent totals, with pending activity shown separately.

In Forecaster you would see estimates, their coverage warnings, approved schedules, explicitly tracked occurrences and a separate list of **bill payments cleared during today and the preceding six civil dates**. Ordinary expenses never enter that list based on their merchant name. Linking a payment covers its obligation rather than posting another debit. Pending and partial payments cannot falsely clear a bill. Deleting a bill payment reopens its tracked obligation; reviewed restoration restores the original entry once.

You could inspect a statement discrepancy without saving anything, see pending entries excluded, make legitimate corrections through Ledger review, and then reconcile an agreeing statement. Locked periods remain protected. Reconciliation records are preserved and included in JSON export. The investigator test caught a liability display-sign mistake during development; the corrected calculation uses positive owed consistently with the existing balance model.

Navigation links survive reload. Another open tab refreshes from the authenticated server after changes, and sign-out clears its private workspace. You can dismiss, snooze or mark individual setup reminders not applicable. Exact review and the two-stage keyboard/tap alternative remain available. Saved proposals and receipts can be revisited; unsent form contents are not durably stored across closing the browser.

## Stage checkpoints and architecture

| Stage                   | Implemented checkpoint                                                                                                                                                                                                                                           | Remaining contract work                                                                                                                                                                                           |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1: storage and identity | Shared asynchronous finance service; locally tested PostgreSQL RLS and non-bypass roles; verified provider signup/recovery; session revocation; encrypted drafts; transactional approvals and receipt recovery                                                   | Hosted project configuration and degraded-provider recovery rehearsal; full abuse controls/session management; multi-key rotation; explicit SQLite conversion tooling                                             |
| 2: manual finance       | Stable naming/opening corrections; transaction/refund/pending/pair edits; reviewed deletion/restoration; recurrence CRUD/archive and occurrence matching; shared budget charts and forecasts; recent paid bills; civil timezone; exports; statement investigator | Guided complex reconciliation corrections; holiday rules; opt-in discretionary forecasting; account lifecycle/retention/erasure; broader scenario/property validation                                             |
| 3: experience           | Feature components, deep links, Back/Forward, cross-tab invalidation, per-item reminders, receipt preservation, automated accessibility checks                                                                                                                   | Full workspace decomposition, complete calendar/mobile product design, optional passkeys, physical devices and real assistive-technology QA                                                                       |
| 4: operations           | Nonce-based script CSP; fail-closed production fallback; health/readiness; CI expansion; bounded synthetic performance check; encrypted synthetic PostgreSQL restore; operational and privacy/terms drafts                                                       | Hosted backup/restore and key recovery, environment provisioning with separate permission, monitoring/on-call, remaining lint dependency advisory, legal review and independent security/accessibility assessment |

`src/lib/domain.ts` is the exact-money/date engine; `insights.ts` supplies common budget/paid-bill/running-balance results. `finance.ts`, `finance-planning.ts` and `proposal-integrity.ts` enforce immutable reviewed operations and atomic posting. `postgres.ts` scopes each serializable transaction to a server-verified subject; composite foreign keys and native monetary checks supplement FORCE RLS. The server writer credential remains a trusted boundary, never supplied to browsers or Pip. `draft-crypto.ts` encrypts PostgreSQL proposals and before/after snapshots; SQLite remains a development-only plaintext fallback.

Charts, planning forms, reminders, export and statement investigation are separate components. No financial data is broadcast between tabs; tabs fetch current owner-scoped data. Validation uses Zod's supported `jitless` runtime mode: production CSP testing discovered its eval capability probe, and this change eliminates that probe instead of enabling unsafe script evaluation. HTML is dynamically rendered with a fresh script/style nonce. React element style attributes remain allowed; production scripts have neither `unsafe-inline` nor `unsafe-eval`.

## Run and try the candidate

Use Node 24, Docker and this branch. Run `npm ci`, `npm run local:services`, then `npm run dev:postgres`. See [operations](OPERATIONS.md) and [Stage 1](STAGE_1_REPORT.md) for ignored local configuration and test services. Run suites serially because development and production builds share `.next`. SQLite fallback remains `npm run db:migrate` and `npm run dev` for local development only.

Use invented identities and values. Create a checking snapshot of $1,000 dated before today, add a Bills category and a $100 monthly target, then approve a $100 recurring bill due today. First enter an ordinary $5 expense with the same description: it must not appear as a paid bill. Enter and explicitly link the $100 bill payment: balance becomes $895, actual spending $105, the graph is over budget, the paid-bill list contains only $100, and the current bill is not projected twice. Delete the payment through review, then restore it from review history. Export from Settings while recently signed in. A second user starts empty and cannot read the first user's receipt or records. This sequence is automated on both backends.
